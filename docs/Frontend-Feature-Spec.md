# 프론트엔드 화면/기능 명세 (작성 중)

## 목적

Phase 4(Agent 기반 일정 추가 계획)를 설계하기 전에, 프론트엔드에서 실제로 구현하려는 화면과 기능을 먼저 확정한다. 이 문서가 채워지면 그걸 근거로:
- Phase 4에서 추가로 필요한 Agent 동작(무엇을 분석하고, 무엇을 승인받고, 무엇을 백업할지)
- Phase 3에서 미처 다루지 않은 추가 API(혹은 기존 API의 응답 필드 보강)

를 역산해서 정리한다. 아래 각 섹션의 `TODO`를 채워주면 됨 — 빈 칸/질문 형태로 최대한 열어뒀고, 필요하면 섹션을 추가하거나 지워도 됨.

## 1. 공통 요소

- 네비게이션 구조 (역할별로 다른 메뉴가 있는지, 상단바/사이드바 등):
  - 사이드바는 모든 역할이 좌측에 공통으로 볼 수 있다.
    - 다만 dev / manager / student에 따라 사이드바에서 볼 수 있는 탭이 다르다.
    - student: TODO, Team
    - manager: student 기능 + 학생 전체 조회 탭
    - dev: manager 기능 + Agent 별 수동 조작 탭
  - 달력은 그 달의 일정을 보여주며, shared_shedule과 personal_schedule을 색으로 구분해서 표시한다
    - 달력의 특정 날짜의 클릭하면 해당 날짜가 크게 하이라이트되며, 작게 보였던 schedule 들이 더 상세하게 표시된다(이 상태에서 삭제 및 추가, 변경 가능)
    - 달력은 월 단위로 일정을 보여주며, 상단에서 화살표로 월을 이동할 수 있다.
- 로그인 상태 유지 / 자동 재로그인 UX (Phase 2에서 결정한 90일 refresh + silent refresh를 프론트에서 어떻게 체감시킬지):
  - 알아서 채워주기 요망
- 로딩/에러/빈 상태(empty state) 공통 처리 방식:
  - 에러는 팝업창을 띄운다. 빈 상태는 빈 상태로 출력한다.
- 반응형 여부(모바일 대응 필요한지):
  - 모바일은 현재 고려하지 않는다. (대부분의 사용자는 노트북으로 작업할 것으로 예상)

## 2. 화면별 상세 명세

아래 템플릿을 화면마다 복사해서 채우기.

### 2-1. 로그인 / 회원가입 / 이메일 인증

- 진입 경로: 최초 웹사이트 접속 시
- 레이아웃 / 구성 요소: 일반적인 로그인 / 회원가입 / 이메일 인증 화면
- 사용자 인터랙션 (입력값, 버튼, 유효성 검사 등): 일반적인...
- 호출하는 API: 로그인 / 회원가입 관련 API
- 에러/엣지 케이스 (예: 미인증 계정 로그인 시도, 토큰 만료 등): 모두 API에서 처리하고 있음

### 2-2. 학생 대시보드 (달력)

- 진입 경로: 로그인 성공시
- 레이아웃 / 구성 요소 (달력 그리드, 날짜 박스, 일정 박스, 상세 패널/모달 등): 월간 달력, 날짜 박스 내에 일정 박스 표시, 완료 여부 체크로 확인
- 일정 박스 클릭 시 보여줄 정보 / 레이아웃: 단순 확대. 달력 미니 박스에서는 title과 완료 여부만 보이고, 확대(상세)했을 때만 `contents`(내용)까지 보여줌 — API는 이미 `contents`를 항상 내려주고 있고, 프론트가 미니 박스에서만 안 보여주는 것뿐이라 백엔드 변경 불필요. 확대 화면에 일정 추가 버튼, 일정마다 삭제/수정 버튼
- 개인 일정 생성/수정/삭제는 어디서 어떻게 트리거되는지(버튼 위치, 폼 형태): 날짜 클릭 시 나타나는 버튼
- 완료 체크는 어떤 UI로(체크박스? 스와이프? 클릭?): 체크박스
- 이전/다음 달 이동 UX: 달력 상단의 화살표 및 작은 달력 아이콘으로 월/년간 이동
- 호출하는 API (Phase 3에서 이미 만든 것 기준으로 매핑):
  - 달력 진입/월 이동: `GET /schedules?year=&month=`
  - 완료 체크박스 토글: `PUT /schedules/{id}/completion`
  - 개인 일정 생성: `POST /schedules` (kind=personal)
  - 개인 일정 수정: `PATCH /schedules/{id}`
  - 개인 일정 삭제: `DELETE /schedules/{id}`
- 엣지 케이스 (일정 없는 날, 하루에 일정이 너무 많을 때 등): 일정이 없으면 빈 칸으로 표시, 일정이 너무 많으면 최대 4개 표시 후 ... 표시
  - 그 외: 공유 일정을 학생이 확대해도 수정/삭제 버튼은 노출되지 않아야 함(백엔드가 403 처리하지만 프론트에서도 UX상 안 보여주는 게 자연스러움)

### 2-3. 운영진(manager) 대시보드

- 학생 화면과 달라지는 부분만 기술 (동일 부분은 "2-2와 동일" 처리): 달력은 동일
- 사이드바 레이아웃(학생 탭 / 팀 탭 아코디언) 상세: 학생탭: manager / student 아코디언이 있으며, 각각 가나다순으로 정렬
  - 팀 탭: 가나다 순으로 정렬, 아코디언 클릭시 소속 학생 가나다순 정렬
  - **확인된 사항**: 아코디언에는 manager/student가 함께 나열되지만(사람 조회는 가능), **캘린더 전환은 student를 클릭했을 때만** 일어남 — manager 항목은 사람 정보 확인용이고 그 사람의 일정을 보는 기능은 아님
- 학생 선택 시 화면 전환 UX(같은 페이지 내 갱신? 라우팅 변경?): 같은 페이지 내 갱신, 좌측 상단에 "{학생}의 일정" 표시.
- 공유 일정 CRUD는 어디서 트리거되는지(버튼 위치, 폼 형태): 일정 클릭 시 커진 화면에서 생성할 때, 개인/공유 일정 선택 가능
- 호출하는 API:
  - 사이드바 학생/팀 목록: `GET /users/{id}`(개별 조회 시), `GET /teams`, `GET /teams/{id}/members`
  - 특정 학생 달력 조회: `GET /schedules?year=&month=&student_id=`
  - 공유 일정 생성/수정/삭제: `POST/PATCH/DELETE /schedules` (kind=shared)
- 엣지 케이스: manager가 사이드바에서 다른 manager/dev를 클릭했을 때 — 위 결정에 따라 애초에 캘린더 전환 액션 자체가 없어야 함(클릭 무반응 또는 사람 정보만 살짝 보여주는 정도)

### 2-4. 개발자(dev) 대시보드

- 1차 목표: manager와 동일 — 달라지는 부분이 생기면 여기 기술
- 사이드 바에 Agent 탭 추가: 누를 시 별도 창이 뜨며, 각 Agent 별 Textbox와 Agent가 계획한 schedule 추가 계획을 보여주는 칸 존재 -> 승인/거절 버튼 누를 시 그에 맞게 동작
  - 승인: 해당 schedule들을 추가
  - 거절: abort
- **Agent 구조 확정**: Agent는 출처(source)별로 나뉘고, Discord는 다시 채널별 Sub-Agent로 세분화됨
  - Notion Agent — 1개
  - Discord Agent — 채널별로 여러 개 (예: 공지방용, 학습공지방용, 음악추천채널용). 채널마다 업데이트 빈도가 낮아 별도 Agent로 나눠도 부담 없음
  - Phase 4 구현 범위는 Notion + Discord(공지/학습공지 채널)까지. **음악추천채널 Agent는 아직 계획 단계**라 이번 Phase 4에서 구현하지 않음(아래 2-5 하단 참고)

### 2-5. (신규) Agent 기반 일정 추가 관리 화면 — Phase 4 핵심

이 화면이 이번 Phase 4 설계의 핵심 입력입니다. 아래 흐름을 화면 단위로 쪼개서 채워주세요.

**a. 텍스트 입력**
- 어디서 입력하는지(전용 페이지? 모달? 어떤 메뉴 밑에?): 별도 창에서 입력
- 입력 폼 형태(단순 textarea? 출처 구분 필드가 있는지 — Discord/Notion 등): Agent(=출처/채널)별 Textarea 사용 — 위 2-4에서 확정된 대로 Notion 1개 + Discord 채널별로 여러 개
- 제출 후 사용자에게 보여지는 피드백(즉시 분석 결과가 뜨는지, "분석 중" 상태가 있는지): 분석 중 상태 사용, 돌아가는 로딩바 표시

**b. Agent 분석 결과(계획) 조회**
- 계획 목록 화면 형태(리스트? 카드? 테이블?): 카드로 보여준 후 개별 승인 / 거절 버튼
- 계획 하나의 상세 화면에 뭘 보여줄지 (제안된 일정 목록, create/update 구분 등): 일정 title, 날짜, create/update 구분. **delete는 Agent가 제안하지 않음**(사람이 직접 삭제) — create/update만 다룸
  - 하나의 텍스트에서 추출한 카드들은 한 박스 안에 묶어서 표시
  - 근거는 카드별 스니펫이 아니라, **박스 상단에 원문 텍스트(또는 원문으로 이동하는 링크)를 한 번만 표시** — 같은 텍스트에서 나온 카드들이라 스니펫을 각각 만드는 것보다 경제적
- 계획 상태(pending/approved/rejected) 표시 방식: **카드(개별 제안) 단위로 상태를 가짐** — 승인/거부 없을시 pending, 나머진 상태에 따라 표시. (박스 전체가 아니라 카드 하나하나가 pending/approved/rejected를 가짐)

**c. Approve / Reject**
- Approve/Reject 버튼 위치와 확인(confirm) 절차 필요 여부: 카드로 보여진 일정 마다 승인/거절 수행
- Approve 직전에 "백업이 생성됨"을 사용자에게 보여줄지: X
- 부분 승인이 가능한지(계획 안의 일부 항목만 승인/거부) 아니면 계획 전체 단위로만 승인/거부인지: **부분 승인 가능(카드 단위)** — 원래 계획서(Implementation-Plan.md 4-2/4-3)의 "계획 전체 승인/거부" 설계를 카드 단위로 변경. 백업도 카드(승인 1건) 단위로 개별 생성 — 사용자 수가 200명 안팎이라 백업 파일 개수 부담은 크지 않다고 판단
- Approve 후 실제로 반영된 결과를 어떻게 확인시킬지(달력에 바로 반영되는지, 별도 완료 메시지): 달력에 바로 반영, 카드에 Approve 표시
  - 만약 Approve 후 실패 시 경고 팝업 띄우고 pending 처리

**d. 백업 확인 (필요하다면)**
- 백업 파일 목록/내용을 화면에서 확인할 수 있어야 하는지, 아니면 서버 로컬 폴더에만 남아도 되는지: 서버 로컬 폴더에만 남김(현재로선)

**e. (계획 단계, 이번 Phase 4에는 미포함) 음악 추천 채널 Agent**
- Discord 음악추천채널용 Agent는 매일 오전 9시에 전날 추천 목록을 종합해서 자동으로 반영하는 **스케줄 기반 자동 실행**(사람이 텍스트를 붙여넣는 방식이 아님)으로 계획 중
- 우측 사이드바에 "추가 기능" 영역을 만들 예정이며, 그 첫 기능이 이 음악 추천 모음이 될 것으로 예상
- 아직 설계 확정 전이라 Phase 4 구현 범위에서는 제외. Phase 4의 크롤링 파이프라인(수동 실행/스케줄 실행이 같은 함수 공유하도록 설계하라는 기존 계획, Implementation-Plan.md 4-6)을 짤 때 이런 "채널별 스케줄 + 다른 종류의 콘텐츠(일정이 아니라 추천 목록)"도 나중에 얹을 수 있는 구조인지는 염두에 두면 좋음

| 학생 달력 조회/월 이동 | `GET /schedules?year=&month=` | 있음 | |

## 4. Phase 4 Agent 설계에 영향 주는 질문들

- Claude API에 텍스트를 넘길 때, 어떤 형태의 출력(JSON 스키마)을 기대하는지 — 화면 2-5b에서 보여줄 정보와 맞물림:
  - textarea에 입력후 넘겨주면 LLM API가 처리 후 JSON 형식으로 돌려주고, 이를 파싱하여 계획 카드 생성
  - tools description을 사용해 출력 내용 설명 및 Pydantic response 강제로 검증, 반드시 카드가 생성되는 출력으로 받아옴
- 계획이 여러 번 재실행(재분석)될 수 있는지, 아니면 한 번 만든 계획은 고정인지:
  - 파싱 실패시 3회까지 재분석, 계속 실패시 결과에 파싱 실패 표시
- 자동 크롤링(MVP 이후) 화면도 지금 같이 설계할지, 완전히 나중으로 미룰지:
  - 자동 크롤링 버튼은 생성, 기능은 X (단, 음악추천채널 Agent는 예외적으로 매일 9시 자동 실행이 계획되어 있음 — 2-5e 참고. 이건 "버튼 눌러서 수동 실행"이 아니라 스케줄 자체가 핵심 기능이라 별개로 취급)
- Agent가 여러 개(Notion 1 + Discord 채널별 N개)인데, 이걸 데이터/코드 구조에서 어떻게 구분할지:
  - `crawl-texts`에 `source`(notion/discord)와 `channel`(discord일 때만, 예: 공지방/학습공지방) 필드 필요
  - 채널마다 분석 프롬프트가 다를 수 있음(예: 음악채널은 아예 다른 종류의 콘텐츠) — Claude API 호출 함수는 공유하되 프롬프트/스키마를 채널 타입별로 다르게 구성하는 구조를 고려
- 카드(제안 항목) 단위 승인이 되면서, 원래 `Schedule_Plan.status` 하나로 관리하려던 게 카드 레벨로 내려가야 함:
  - 새 테이블(가칭 `ScheduleProposal`)이 필요해 보임: `proposal_id, raw_text_id(FK), action(create/update), title, contents, deadline, target_schedule_id(update일 때만), status(pending/approved/rejected), created_at, updated_at`
  - 원문 텍스트(`raw_text_id`)로 묶어서 카드 여러 개를 한 박스에 표시

## 5. 결정 로그 (이 문서를 채우며 새로 확정되는 것들)

이 문서 작성 중에 나온 결정/변경 사항을 여기에 짧게 기록 (나중에 `Implementation-Plan.md`/PRD에 반영할 때 근거로 사용).

- **승인 단위를 "계획 전체"에서 "카드(개별 제안 항목) 단위"로 변경.** 백업도 카드 단위로 개별 생성(사용자 200명 안팎 규모라 파일 개수 부담 적음 판단).
- **Agent 구조: Notion 1개 + Discord는 채널별 Sub-Agent(공지방/학습공지방/음악추천채널 등)로 세분화.** 채널당 업데이트 빈도가 낮아 부담 없음.
- **음악추천채널 Agent(매일 9시 자동 종합)는 계획 단계 — 이번 Phase 4 구현 범위에서 제외.** 우측 사이드바 "추가 기능" 영역의 첫 기능으로 나중에 추가 예정.
- **근거 표시 방식: 카드별 스니펫 대신, 원문 텍스트(또는 링크)를 박스 상단에 한 번만 표시.**
- **Agent는 delete를 제안하지 않음 — create/update만.** 삭제는 항상 사람이 직접 수행.
- **사이드바 아코디언(manager/student)에서 "사람 조회"와 "그 사람 캘린더 보기"는 별개** — 캘린더 전환은 student 클릭 시에만 발생, manager 항목은 정보 열람용.
- **`contents` 필드는 백엔드에 이미 구현돼 있고 스키마 변경 불필요** — 학생 달력의 미니 박스에서만 안 보여주고 확대했을 때만 노출하는 프론트 표시 방식의 문제였음.
